# mydevexblog

Field notes on developer experience from 7+ years in DevOps and platform engineering — CI/CD, Kubernetes, and the friction points nobody talks about.

Live site: https://vivek-itp.github.io/mydevexblog/

Built with [MkDocs](https://www.mkdocs.org/) and the [Material](https://squidfunk.github.io/mkdocs-material/) theme. Every push to `main` rebuilds and publishes the site through GitHub Pages, so publishing a post is just a commit.

## Writing a new post

1. Create a Markdown file in `docs/blog/posts/`. Name it after the date and title, e.g. `2026-10-01-my-post.md`.
2. Start the file with a front-matter block:

   ```yaml
   ---
   title: My post title
   date:
     created: 2026-10-01
   authors:
     - vivek
   categories:
     - CI/CD            # must be one of the categories listed in mkdocs.yml
   tags:
     - ci
   ---
   ```

3. Write the post below the front matter in plain Markdown. Put `<!-- more -->` on its own line after the first paragraph or two; everything above it becomes the preview on the blog index.
4. Commit and push to `main`. The site updates in about a minute.

If the post contains a diagram (a ```` ```mermaid ```` block), run `python tools/render_diagrams.py` before committing. It renders the diagram to a PNG under `docs/assets/diagrams/` so the post can be imported into Medium and dev.to, which cannot draw diagrams themselves. The site shows the PNG when it exists and draws the diagram live when it does not. Rendering needs Node.js.

To keep a post private while you work on it, add `draft: true` to the front matter. Draft posts are visible when you preview locally but never get published. The three files starting with `draft-` in `docs/blog/posts/` are skeletons you can fill in.

## Previewing locally

```bash
python3 -m venv .venv
source .venv/bin/activate      # on Windows: .venv\Scripts\activate
pip install -r requirements.txt
mkdocs serve
```

Open http://127.0.0.1:8000 in your browser. The page reloads on every save.

Run `mkdocs build --strict` before pushing if you want to catch broken links early. It is the same command the deploy workflow uses.

## Cross-posting

- **dev.to** is automatic. After every deploy, the workflow publishes new posts and updates changed ones on dev.to, with the canonical link pointing back to this site. It needs a repository secret named `DEVTO_API_KEY` (dev.to: Settings, Extensions, Generate API Key). Without the secret the step does nothing.
- **Medium** has no API for new accounts. After a post is live, open Medium, click your profile picture, then Stories, then "Import a story", and paste the post's URL. Medium keeps the original date and canonical link.

## Layout

```
mkdocs.yml               site settings, theme, plugins, navigation
requirements.txt         pinned Python dependencies
docs/index.md            home page
docs/about.md            about page
docs/blog/index.md       blog landing page (generated by the plugin)
docs/blog/.authors.yml   author profiles shown on posts
docs/blog/posts/         one Markdown file per post
docs/stylesheets/        small CSS tweaks
hooks/diagrams.py        build hook: swaps mermaid blocks for rendered PNGs
tools/render_diagrams.py renders mermaid blocks to PNG (run after editing a post)
tools/publish_devto.py   publishes posts to dev.to (runs in the workflow)
POST_QUEUE.md            upcoming topics for the scheduled drafting job
.github/workflows/       GitHub Actions workflow that builds, deploys, and cross-posts
```
